# Bitlite

| 🇺🇸 [English](README.md) | 🇮🇷 [فارسی](README-FA.md) |
|--------------------------|----------------------------|

<div dir="rtl">

Bitlite یک پروکسی Stratum V1 برای ماینرهای ASIC الگوریتم SHA-256 است که با یک رابط مدیریت تحت وب، در قالب یک فایل Go و یک کانتینر Docker ارائه می‌شود. ماینرها با TCP یا TLS به پروکسی وصل می‌شوند. پروکسی برای هر ماینر اتصال جداگانه‌ای به استخر فعال باز می‌کند، نام ورکر را به حساب استخر بازنویسی می‌کند و وقتی استخر را عوض کنید یا استخر از دسترس خارج شود، مزرعه را به استخر دیگر منتقل می‌کند.

Bitlite روی این پروکسی چیزهایی اضافه می‌کند که میزبان یک مزرعه وقتی ماینر دیگران روی آن کار می‌کند به آن‌ها نیاز دارد: مشتری‌ها و دستگاه‌هایی که شما تأیید می‌کنید (با زمان پایان)، نقش‌ها و گزارش رویدادها (audit)، «سهم اپراتور» اختیاری و شفاف، و رابط و ربات تلگرام فارسی (راست‌به‌چپ) در کنار انگلیسی و روسی.

Bitlite یک فورک از [famfamfam/simple-mining-proxy](https://github.com/famfamfam/simple-mining-proxy) با همان مجوز GPL-3.0 است و هر کاری که پروکسی اصلی می‌کرد حفظ شده است.

برای استخرهای BTC و BCH نوشته شده است. استخرهای XEC و DigiByte (SHA-256) و Fractal Bitcoin که Stratum V1 استاندارد را بفهمند هم باید کار کنند: پروکسی داخل jobها و بلاک‌ها را نمی‌خواند و فقط پیام‌های Stratum را رد و بدل می‌کند.

## امکانات

- شنونده‌های Stratum روی TCP و TLS هم‌زمان (`stratum+tls` که `stratum+ssl` هم نوشته می‌شود).
- اتصال TCP یا TLS به هر استخر، مستقل از روش اتصال ماینر.
- `mining.authorize` و فیلد worker در `mining.submit` به حساب استخر انتخاب‌شده بازنویسی می‌شود؛ بقیه‌ی فیلدها (از جمله بیت‌های version-rolling) بدون تغییر عبور می‌کنند.
- یک استخر فعال و فهرست مرتب استخرهای پشتیبان، با بررسی سلامت، failover و بازگشت با تأخیر.
- چند آدرس برای هر استخر؛ نشست‌های جدید به سریع‌ترین آدرس سالم می‌روند.
- جابه‌جایی استخر، ماینرها را به‌تدریج و در یک بازه‌ی قابل‌تنظیم دوباره وصل می‌کند.
- شمارش شیرهای پذیرفته و ردشده، دلیل ردشدن و برآورد نرخ هش، برای هر استخر و هر ماینر؛ نمودارهای تاریخچه از یک ساعت تا یک سال.
- جابه‌جایی بر اساس سود بین کوین‌های SHA-256 (اختیاری)، جابه‌جایی زمان‌بندی‌شده، و شکار بلاک در eCash (اختیاری).
- هشدار وقتی ASIC شیر نمی‌فرستد و وقتی برمی‌گردد: در رویدادها و، با ربات تنظیم‌شده، در تلگرام.
- تنظیمات زمان اجرا با توضیح و اعتبارسنجی، بدون نیاز به راه‌اندازی دوباره.
- گواهی TLS خودامضا در اولین راه‌اندازی یا گواهی خودتان؛ محدودیت اتصال و timeout در برابر کلاینت‌های کند یا خراب.
- رابط مدیریت به انگلیسی، روسی و فارسی (راست‌به‌چپ) که روی گوشی هم کار می‌کند، با تم روشن و تیره. هر کاری که رابط می‌کند از طریق REST API هم ممکن است.

افزوده‌های Bitlite:

- **مشتری‌ها و دستگاه‌ها:** ماینر با نام `<مشتری>.<ورکر>` و کلید اتصال مشتری وارد می‌شود. دستگاه تازه منتظر تأیید شما می‌ماند و برایش زمان کار تعیین می‌کنید (یک هفته، یک ماه، ... یا بدون پایان). می‌توانید آن را معلق، مسدود، ازسرگرفته یا لغو کنید. مسدودکردن یک دستگاه به دستگاه‌های تأییدشده‌ی دیگر همان مشتری دست نمی‌زند.
- **کاربران، نقش‌ها و گزارش رویدادها (audit):** چه کسی، چه کاری، چه وقت.
- **سهم اپراتور (اختیاری):** پیش‌فرض خاموش، با رضایت ثبت‌شده‌ی مشتری، سقف و حساب هر پنجره‌ی زمانی.
- **بررسی ورکر دوم:** ابزاری برای دیدن اینکه استخر ورکر دوم را روی یک اتصال می‌پذیرد یا نه.
- رابط و ربات تلگرام فارسی، و تقویم شمسی اختیاری برای نمایش تاریخ‌ها.

## راه‌اندازی سریع

به Docker Engine با Compose v2 نیاز دارید.

</div>

```bash
git clone https://github.com/clonerdev/simple-mining-proxy.git
cd simple-mining-proxy
cp .env.example .env
```

<div dir="rtl">

حداقل این‌ها را در `.env` تنظیم کنید:

- `ADMIN_PASSWORD`: یک رمز طولانی و یکتا؛
- `PUBLIC_HOST`: آدرس IP یا نام DNS که ماینرها به آن وصل می‌شوند؛
- `TLS_SELF_SIGNED_HOSTS`: نام‌های DNS و IPهایی که ماینرها برای پورت TLS استفاده می‌کنند.

اجرا:

</div>

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f proxy
```

<div dir="rtl">

پورت‌هایی که `docker-compose.yml` منتشر می‌کند:

| کاربرد | آدرس پیش‌فرض روی میزبان |
|---|---|
| Stratum TCP | `0.0.0.0:13333` |
| Stratum TLS | `0.0.0.0:14443` |
| رابط مدیریت و API | `127.0.0.1:18080` |

استخرها، تنظیمات، گواهی‌ها و تاریخچه در volume داکر ذخیره می‌شوند. لاگ‌های کانتینر به پنج فایل ۱۰ مگابایتی محدود است.

## رابط مدیریت

پورت مدیریت فقط روی localhost گوش می‌دهد. با تونل SSH به آن برسید:

</div>

```bash
ssh -L 18080:127.0.0.1:18080 user@your-server
```

<div dir="rtl">

آدرس http://127.0.0.1:18080 را باز کنید و با `ADMIN_USERNAME` و `ADMIN_PASSWORD` وارد شوید. نشست‌ها ۱۲ ساعت در حافظه می‌مانند و با راه‌اندازی دوباره‌ی پروسه پایان می‌یابند. رابط HTTP ساده است؛ اگر باید از اینترنت در دسترس باشد، آن را پشت یک reverse proxy با HTTPS بگذارید یا از تونل استفاده کنید. ورودهای ناموفق محدود می‌شوند: بعد از ۵ شکست در ۱۵ دقیقه آدرس مسدود می‌شود (۱۵ دقیقه، سپس ۳۰ دقیقه، ۱ ساعت و تا ۲۴ ساعت).

## تنظیم اولیه

1. در داشبورد، استخر اصلی را اضافه کنید: نام، کوین، آدرس‌ها، قالب نام ورود و رمز. هر خط آدرس یک `host:port` است. پروکسی زمان اتصال به هر آدرس را می‌سنجد و نشست‌های تازه را به سریع‌ترین آدرس سالم می‌فرستد.
2. اگر استخر TLS می‌خواهد آن را انتخاب کنید. چسباندن آدرسی با `stratum+tcp://` یا `stratum+tls://` نوع اتصال را خودکار تعیین می‌کند. تأیید گواهی به‌طور پیش‌فرض روشن است.
3. دکمه‌ی «آزمایش» قبل از ذخیره، روی هر آدرس متصل می‌شود، `mining.subscribe` و `mining.authorize` را با ورکر آزمایشی می‌فرستد و منتظر یک `mining.notify` قابل‌استفاده می‌ماند. بعد استخر را ذخیره و فعال کنید.
4. استخرهای پشتیبان را اضافه و ترتیبشان را تعیین کنید.
5. آدرس TCP یا TLS داشبورد را در ماینرها بگذارید:

</div>

```text
stratum+tcp://proxy.example.com:13333
stratum+tls://proxy.example.com:14443
```

<div dir="rtl">

`stratum+tls` و `stratum+ssl` یکی هستند. Whatsminer فقط `stratum+tls` را می‌پذیرد و بعضی فریم‌ورهای دیگر فقط `stratum+ssl` را.

## نام ورکر

قالب نام ورود استخر می‌تواند این‌ها را داشته باشد: `{worker}` (بخش بعد از اولین نقطه‌ی نام ورود ماینر)، `{login}` (کل نام ورود) و `{password}`. با قالب `account.{worker}` ماینری که با `farm.S21-0042` وارد شده، روی استخر `account.S21-0042` کار می‌کند. هر `mining.authorize` معتبری که از پروکسی بگذرد به نام و رمز استخر انتخاب‌شده بازنویسی می‌شود.

## مشتری‌ها و کنترل دستگاه

کنترل دستگاه به‌طور پیش‌فرض **خاموش** است و پروکسی مثل نسخه‌ی اصلی برای همه‌ی ماینرها باز است. برای اینکه فقط دستگاه‌های تأییدشده استخراج کنند، `device_control` را در تنظیمات (بخش دستگاه‌ها) روشن کنید.

1. در صفحه‌ی «دستگاه‌ها» یک مشتری اضافه کنید: نام کوتاه (slug)، نام حساب استخر (اختیاری)، محدودیت‌ها و تاریخ پایان (اختیاری). **کلید اتصال** مشتری فقط یک‌بار، هنگام ساخت یا تغییر، نمایش داده می‌شود. خود کلید ذخیره نمی‌شود، فقط هش آن.
2. مشتری ماینرها را به پروکسی وصل می‌کند و با نام `<slug>.<worker>` و کلید اتصال به‌جای رمز وارد می‌شود.
3. دستگاه تازه «در انتظار تأیید» ثبت می‌شود و استخراج نمی‌کند. شما آن را تأیید می‌کنید و مدت کارش را تعیین می‌کنید: یک هفته، یک ماه، سه ماه، شش ماه، یک سال، بدون پایان یا تاریخ دلخواه. رد، تعلیق، ازسرگیری، مسدودسازی، رفع مسدودیت و لغو هم هست. زمان پایان بعداً قابل تغییر است.
4. همه‌چیز روی سرور و در هر ورود و هر تغییر وضعیت بررسی می‌شود: دستگاهی که تأیید نشده، منقضی شده یا مشتری‌اش معلق یا مسدود است، اتصال‌هایش بسته می‌شود. مسدودکردن یک دستگاه هرگز دستگاه‌های تأییدشده‌ی دیگر مشتری را قطع نمی‌کند.

کلید اشتباه با دستگاه در انتظار فرق دارد: ورود با کلید اشتباه به‌ازای هر آدرس شمرده می‌شود و پس از تعداد زیاد، آن آدرس مدتی مسدود می‌شود. دستگاهی که کلید درست دارد و فقط منتظر تأیید است شکست حساب نمی‌شود تا مشتری‌های پشت یک NAT همدیگر را قفل نکنند.

مشتری‌ها به پنل دسترسی ندارند و همه‌چیز را فقط مدیر انجام می‌دهد.

تنظیمات: `device_control` (خاموش)، `device_auth_timeout` (۳۰ ثانیه)، `device_pending_limit` (۱۰ دستگاه منتظر برای هر مشتری).

## سهم اپراتور (اختیاری)

سهم اپراتور به میزبان مزرعه اجازه می‌دهد بخش کوچک و ثابتی از **زمان استخراج** مشتری را به‌عنوان کار برای ورکر خودش بردارد. هیچ پولی جابه‌جا نمی‌کند: استخر به کسی پول می‌دهد که شیر به نام او ثبت شده و Bitlite فقط می‌نویسد چه مقدار کار به کجا رفته است. هرگز استخراج مشتری را بدون اطلاع و توافق او منحرف نمی‌کند.

به‌طور پیش‌فرض خاموش است و شیر فقط وقتی به اپراتور می‌رود که **همه‌ی** این شرایط برقرار باشد (برای هر شیر روی سرور بررسی می‌شود):

- `operator_share` در تنظیمات روشن باشد؛
- استخر در ویرایشگر به‌عنوان «ورکر دوم را اعتبار می‌دهد» علامت خورده و ورود اپراتور برای آن استخر وارد شده باشد؛
- رضایت مشتری را در صفحه‌ی «دستگاه‌ها» ثبت کرده باشید (چه کسی و با چه شرایطی ثبت کرده در audit می‌ماند و با پس‌گرفتن آن، سهم فوراً قطع می‌شود)؛
- دستگاه تأییدشده باشد و قانون برای آن سهمی بیشتر از صفر بدهد.

روش کار: در پنجره‌های کوتاه و ثابتِ هر چرخه (`operator_share_cycle`، پیش‌فرض ۱۵ دقیقه) پروکسی در فیلد worker پیام `mining.submit` به‌جای ورکر مشتری، ورکر اپراتور را می‌گذارد. ماینر هیچ‌وقت متوقف یا قطع نمی‌شود. اندازه درصدی از زمان یا دقیقه در روز است (یک ساعت در روز حدود ۴٫۱۷٪) و هر چه قانون بگوید با `operator_share_max_percent` (پیش‌فرض ۱۰٪) سقف می‌خورد.

اندازه را می‌توان برای کل پروکسی (تنظیمات)، برای هر مشتری و برای هر دستگاه تعیین کرد. اولویت با قانون خود دستگاه است، بعد قانون مشتری، بعد تنظیمات؛ مقدار ۰ آن مشتری یا دستگاه را کنار می‌گذارد. تعیین اندازه به دسترسی `billing.manage` نیاز دارد و در audit ثبت می‌شود. اندازه هیچ‌وقت جای رضایت را نمی‌گیرد.

صفحه‌ی «سهم اپراتور» برای هر بازه و هر مشتری زمان داده‌شده به اپراتور، تعداد پنجره‌ها و شیرهای پذیرفته و ردشده را نشان می‌دهد و جدول را می‌توان به CSV گرفت. درآمد و پرداخت نشان نمی‌دهد، چون Bitlite آن‌ها را نمی‌بیند.

اگر استخر ورکر اپراتور را نپذیرد یا شیرهایش را رد کند، سهم برای مدتی روی آن استخر خودش را خاموش می‌کند و صفحه دلیلش را می‌گوید؛ استخراج مشتری مثل قبل ادامه می‌یابد.

**مهم:** این قابلیت فقط با استخری کار می‌کند که ورکر دوم را روی همان اتصالِ ماینر بپذیرد و برایش شیر ثبت کند. مستندات استخرها در این باره چیزی نمی‌گویند و برای ViaBTC این موضوع **تأیید نشده است**. تا وقتی خودتان روی یک حساب آزمایشی بررسی نکرده‌اید، به آن تکیه نکنید و به مشتری نگویید که کار می‌کند.

### بررسی استخر برای سهم اپراتور

در ویرایشگر استخر، با تیک سهم اپراتور و ورود اپراتور، دکمه‌ی **«بررسی ورکر دوم»** به هر آدرس وصل می‌شود، با ورکر آزمایشی وارد می‌شود و بعد `mining.authorize` اپراتور را روی همان اتصال می‌فرستد، دقیقاً مثل یک نشست واقعی. هر مرحله را نشان می‌دهد: اتصال، subscribe، احراز، job، احراز دوم و باز ماندن اتصال. نتیجه یکی از این‌هاست: احراز دوم پذیرفته شد، رد شد (با دلیل استخر)، پاسخی نیامد، اتصال بسته شد، یا به این مرحله نرسید.

این ابزار هیچ شیری نمی‌فرستد، پس **نمی‌تواند** ثابت کند که استخر شیرها را به ورکر دوم می‌دهد؛ ممکن است استخر ورود دوم را بپذیرد و باز همه‌چیز را به ورکر اول بدهد. برای اطمینان:

1. از یک حساب آزمایشی در همان استخر استفاده کنید، نه حساب مشتری.
2. سهم اپراتور را روشن کنید، رضایت یک دستگاه آزمایشی را ثبت کنید و کمی از طریق پروکسی استخراج کنید.
3. داشبورد خود استخر را باز کنید: ورکر اپراتور باید شیرهای پذیرفته‌شده‌ی خودش را نشان دهد.

## کاربران، نقش‌ها و گزارش رویدادها

مدیری که با `ADMIN_USERNAME` و `ADMIN_PASSWORD` وارد می‌شود می‌تواند حساب‌های دیگر بسازد. نقش مجموعه‌ای از دسترسی‌هاست: `superadmin` همه را دارد و `operator` می‌تواند مزرعه را ببیند و دستگاه‌ها را مدیریت کند ولی تنظیمات و حساب‌ها را نه. دسترسی‌ها را می‌توان برای هر حساب اضافه یا کم کرد:

| دسترسی | اجازه می‌دهد |
|---|---|
| `stats.view`، `miners.view`، `events.view` | داشبورد، نمودارها، ماینرها، رویدادها |
| `miners.control` | اتصال دوباره‌ی همه‌ی ماینرها |
| `settings.view`، `settings.edit` | دیدن و تغییر استخرها، تنظیمات و ربات |
| `devices.view`، `devices.manage` | دیدن، تأیید، مسدودسازی و محدودکردن مشتری‌ها و دستگاه‌ها |
| `billing.view`، `billing.manage` | حساب سهم اپراتور؛ رضایت و اندازه‌ی سهم |
| `audit.view` | گزارش رویدادها (audit) |
| `users.manage` | حساب‌ها، نقش‌ها و رمزها |

گزارش audit ورودها، درخواست‌های ردشده و تغییرات کاربران، مشتری‌ها، دستگاه‌ها، استخرها و تنظیمات را با حساب، آدرس، هدف، نتیجه و جزئیات ثبت می‌کند. رمزها، کلیدها و توکن‌ها هرگز ثبت نمی‌شوند. صفحه‌ی آن بر اساس بازه، گروه کار، نتیجه و متن فیلتر می‌کند و خروجی CSV می‌دهد.

## تنظیمات زمان اجرا

بقیه‌ی تنظیمات در صفحه‌ی «تنظیمات» (یا با `PUT /api/settings`) تعیین می‌شود، در `state.json` ذخیره می‌شود و بدون راه‌اندازی دوباره اعمال می‌شود. اگر یکی از مقادیر یک تغییر نامعتبر باشد، هیچ‌چیز تغییر نمی‌کند. فهرست کامل با پیش‌فرض‌ها و بازه‌ها در [README انگلیسی](README.md#runtime-settings) است؛ مهم‌ترین‌ها:

| تنظیم | پیش‌فرض | معنا |
|---|---|---|
| `test_worker` | `proxytest` | نام ورکر برای بررسی استخرها |
| `switch_drain` | ۱۰ ثانیه | بازه‌ای که قطع اتصال‌ها هنگام جابه‌جایی در آن پخش می‌شود |
| `failback_delay` | ۲ دقیقه | مدتی که استخر فعال باید سالم بماند تا نشست‌ها به آن برگردند |
| `device_control` | خاموش | فقط مشتری‌ها و دستگاه‌های تأییدشده استخراج کنند |
| `operator_share` | خاموش | کلید سهم اپراتور |
| `operator_share_max_percent` | ۱۰٪ | سقف همه‌ی اندازه‌ها |
| `telegram_language` | en | زبان هشدارها و پاسخ‌های ربات: en، ru یا fa |
| `max_conn_per_ip` | ۰ (خاموش) | حداکثر اتصال از یک IP |
| `tls_min_version` | 1.2 | قدیمی‌ترین نسخه‌ی TLS مجاز |

## متغیرهای محیطی

این‌ها پروسه را پیکربندی می‌کنند و بعد از راه‌اندازی دوباره‌ی کانتینر اعمال می‌شوند:

| متغیر | پیش‌فرض | کاربرد |
|---|---|---|
| `STRATUM_TCP_ADDR` | `:13333` | آدرس شنونده‌ی Stratum TCP؛ `off` خاموش می‌کند |
| `STRATUM_TLS_ADDR` | `:14443` | آدرس شنونده‌ی Stratum TLS؛ `off` خاموش می‌کند |
| `ADMIN_ADDR` | `:18080` | آدرس رابط مدیریت و API |
| `ADMIN_USERNAME` | `admin` | نام کاربری مدیر |
| `ADMIN_PASSWORD` | الزامی | رمز مدیر |
| `API_TOKEN` | خالی | توکن Bearer برای کلاینت‌های API؛ خالی یعنی ورود با توکن غیرفعال |
| `DATA_DIR` | `/data` | پوشه‌ی داده، تاریخچه و گواهی‌ها |
| `TLS_CERT_FILE`، `TLS_KEY_FILE` | `/data/certs/...` | گواهی و کلید شنونده‌ی TLS |
| `TLS_SELF_SIGNED_HOSTS` | نام میزبان کانتینر | نام‌های گواهی خودامضا، جدا با کاما |

| `TELEGRAM_API_URL` | `https://api.telegram.org` | سرور Bot API، برای سرور محلی یا آینه |

## گواهی TLS

اگر `/data/certs/fullchain.pem` و `/data/certs/privkey.pem` نباشند، اولین راه‌اندازی یک گواهی خودامضای ۱۰ ساله برای نام‌های `TLS_SELF_SIGNED_HOSTS` می‌سازد. برای گواهی معتبر، هر دو فایل را در کانتینر mount کنید (خواندنی برای UID ‏65532) و `TLS_CERT_FILE` و `TLS_KEY_FILE` را تنظیم کنید؛ جفت تغییرکرده بدون راه‌اندازی دوباره برداشته می‌شود. ماینرها به‌طور پیش‌فرض باید TLS نسخه‌ی ۱٫۲ یا بالاتر داشته باشند.

## نکته‌های فریم‌ور

| فریم‌ور | نکته |
|---|---|
| Antminer اصلی | از پورت TCP استفاده کنید؛ فریم‌ور اصلی بسیاری از مدل‌ها نمی‌تواند با TLS به سرور Stratum دلخواه وصل شود. |
| Whatsminer اصلی | TLS کار می‌کند و M50 گواهی خودامضا را می‌پذیرد. مدل‌ها و نسخه‌های دیگر شاید نپذیرند؛ آن‌وقت از گواهی معتبر یا TCP در شبکه‌ی مطمئن استفاده کنید. |
| VNish | TLS را روی نسخه‌ی خودتان بررسی کنید. اتصال‌های dev-fee که خود فریم‌ور باز می‌کند از پروکسی نمی‌گذرد. |
| WMOC | TCP و TLS را روی نسخه‌ی خودتان بررسی کنید. |

## جابه‌جایی بر اساس سود، زمان‌بندی‌شده و شکار بلاک

این بخش‌ها از پروژه‌ی اصلی مانده‌اند و تغییری نکرده‌اند؛ توضیح کامل آن‌ها (قاعده‌ی Real Time Targeting در eCash، استخر اصلی، استخرهای solo، پنجره‌های زمانی) در [README انگلیسی](README.md#profit-switching) است. خلاصه:

- **جابه‌جایی بر اساس سود:** پروکسی کوین‌های SHA-256 استخرهای شما را با داده‌ی WhatToMine و WhatsOnChain در بازه‌ی تعیین‌شده مقایسه می‌کند و فقط توصیه می‌دهد (advise) یا خودش جابه‌جا می‌کند (auto). کارمزد و روش پرداخت استخرها در نظر گرفته نمی‌شود. در استخرهای PPLNS جابه‌جایی مکرر درآمد را کم می‌کند.
- **جابه‌جایی زمان‌بندی‌شده:** بخشی از هر دوره، مثلاً ۱۰ دقیقه از هر ۳۰ دقیقه، روی استخر دیگری (مثلاً solo) کار می‌کند و برمی‌گردد.
- **شکار بلاک در eCash:** مزرعه فقط وقتی روی استخر solo ‏XEC کار می‌کند که بلاک بعدی از هدف هدر سخت‌تر نباشد و با پیداشدن بلاک برمی‌گردد.

هر جابه‌جایی همه‌ی ماینرها را در `switch_drain` دوباره وصل می‌کند.

## هشدار و پایش

ASIC سالم هر چند ثانیه شیر می‌فرستد. اگر مدتی بیشتر از `offline_after` (پیش‌فرض ۱ دقیقه) شیری نفرستد، آفلاین حساب می‌شود. تغییرها در رویدادها می‌آیند. برای تلگرام، در تنظیمات بخش «پایش و هشدار»: با [@BotFather](https://t.me/BotFather) یک ربات بسازید و توکنش را وارد کنید، از چت خود `/start` بفرستید، شناسه‌ی چت را در `telegram_chats` بگذارید و زبان را انتخاب کنید. ربات خودش پیام‌ها را از تلگرام می‌گیرد (long polling) و به آدرس عمومی نیاز ندارد. دستورها: `/status`، `/miners`، `/help`. توکن در `state.json` می‌ماند و API هرگز آن را برنمی‌گرداند. به هر ASIC نام یکتا بدهید، چون ASICهای هم‌نام یکی شمرده می‌شوند.

## API

رابط مدیریت از یک API با قالب JSON زیر `/api/` استفاده می‌کند. اسکریپت‌ها با `Authorization: Bearer <API_TOKEN>` وارد می‌شوند و درخواست‌های تغییردهنده باید `Content-Type: application/json` داشته باشند. فهرست کامل مسیرها در [README انگلیسی](README.md#api) است. مسیرهای Bitlite:

| مسیر | کاربرد |
|---|---|
| `GET /api/users`، `GET /api/roles` | حساب‌ها، نقش‌ها و دسترسی‌ها |
| `GET /api/audit` | گزارش رویدادها؛ با `format=csv` فایل CSV |
| `GET`/`POST /api/customers` | مشتری‌ها؛ کلید اتصال فقط هنگام ساخت برمی‌گردد |
| `POST /api/customers/{id}/fee-consent` | ثبت یا پس‌گرفتن رضایت |
| `PUT /api/customers/{id}/operator-share` و `PUT /api/devices/{id}/operator-share` | اندازه‌ی سهم اپراتور: `{"kind":"percent","amount":3}` یا `{"inherit":true}` |
| `GET /api/devices`، `POST /api/devices/{id}/action` | دستگاه‌ها؛ تأیید، تعلیق، مسدودسازی ... با `expires_at` اختیاری |
| `POST /api/pools/test-operator` | بررسی ورکر دوم روی یک اتصال |
| `GET /api/operator-share/usage` | حساب سهم اپراتور به‌ازای دستگاه و روز |

خطاها شکل `{"error": "validation", "key": "...", "params": {...}, "message": "..."}` دارند.

## شبکه و فایروال

پورت‌های Stratum را تا جایی که می‌شود فقط برای IPهای مزرعه‌ها باز کنید. پورت‌هایی که Docker منتشر می‌کند قاعده‌های UFW را دور می‌زنند؛ از فایروال ارائه‌دهنده یا زنجیره‌ی `DOCKER-USER` در iptables استفاده کنید. `max_conn_per_ip` پیش‌فرض خاموش است، چون یک مزرعه معمولاً از یک آدرس NAT وصل می‌شود.

پروکسی برای داده‌ی بازار درخواست HTTPS خروجی به whattomine.com و api.whatsonchain.com می‌زند (با جابه‌جایی بر اساس سود روشن) و با ربات تلگرام، یک درخواست long polling به api.telegram.org باز نگه می‌دارد.

## نکته‌های امنیتی

- پورت مدیریت را روی localhost نگه دارید و با تونل SSH یا VPN به آن برسید؛ اگر باید از اینترنت در دسترس باشد، پشت reverse proxy با HTTPS بگذارید. خود رابط HTTP ساده است.
- از `ADMIN_PASSWORD` طولانی و یکتا، یک حساب برای هر نفر استفاده کنید و `API_TOKEN` و توکن ربات تلگرام را در متغیر محیطی یا رابط مدیریت نگه دارید، نه در مخزن.
- ASICها را در شبکه‌ای جدا بگذارید که فقط به پروکسی دسترسی دارد و رمز پیش‌فرض پنل خود ASIC را عوض کنید.
- پورت‌های Stratum را فقط برای آدرس‌هایی که ماینرها از آن‌ها وصل می‌شوند باز کنید. هر جا فریم‌ور پشتیبانی می‌کند از پورت TLS استفاده کنید؛ وگرنه بین مزرعه و پروکسی VPN بگذارید.
- وقتی ماینر دیگران وصل می‌شود، `device_control` را روشن کنید تا فقط دستگاه‌های تأییدشده استخراج کنند.
- `state.json` و `devices.json` رمز استخرها، توکن ربات و اطلاعات مشتری‌ها را به‌صورت متن ساده نگه می‌دارند (کلیدهای اتصال فقط به‌صورت هش): از میزبان Docker و پشتیبان‌ها محافظت کنید.

## محدودیت‌ها

- فقط Stratum V1 (JSON-RPC خط‌به‌خط)، بدون Stratum V2.
- یک اتصال استخر برای هر ماینر؛ اتصال‌ها تجمیع نمی‌شوند.
- شمارنده‌های جدول ماینرها بعد از راه‌اندازی دوباره از صفر شروع می‌شوند؛ تاریخچه‌ی نمودارها روی دیسک می‌ماند.
- جابه‌جایی بر اساس سود، کارمزد، روش پرداخت و تأخیر پرداخت استخرها را در نظر نمی‌گیرد.
- ACME / Let's Encrypt داخلی ندارد.
- **سهم اپراتور** استخری می‌خواهد که ورکر دوم را روی یک اتصال بپذیرد و برایش شیر ثبت کند. برای ViaBTC تأیید نشده است: اول روی حساب آزمایشی خودتان امتحان کنید.
- هنوز موتور صورت‌حساب ندارد: Bitlite کار را ثبت می‌کند، نه پول را. فاکتور صادر نمی‌کند و پرداختی را تأیید نمی‌کند.
- مشتری‌ها نمی‌توانند وارد پنل شوند؛ همه‌چیز را مدیران انجام می‌دهند.
- تقویم شمسی فقط برای نمایش و فقط در فارسی است؛ زمان‌های ذخیره‌شده و خروجی‌ها UTC هستند.
- فریم‌ورها، گواهی‌ها و استخرها با هم فرق دارند: قبل از انتقال کل مزرعه چند ماینر را امتحان کنید و نرخ رد را با اتصال مستقیم به استخر مقایسه کنید.
